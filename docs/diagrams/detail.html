kiss-signKeep it simple, stupid, and sign.

Who acts at each step, what it checks, which services it reads, and why the step exists. The AI researches and writes data; the program checks that data and writes the report, and in research decides nothing; at signing the program alone decides the verdict.

SignerStates the intent, reads the report, merges templates, the registry and the program gate, fills and seals the card, proposes, signs.
AI agentWrites data and text: registry entries, the template, docs.json, notes.json. Its text is tagged and never moves a result, a colour or a confidence. It also changes the program, merging only behind the program gate.
ProgramChecks what the AI wrote against the chain and outside sources, records the answers, writes the report, and alone gives the verdict.

Numbered circles are the boxes, in order; “step N” is the step of The flow in docs/design/flow.md.

Program · past-txsstep 4

6Study past transactions

  • Find: a token Transfer (Alchemy Transfers and Etherscan) or an event (Etherscan alone); a Safe's own event counts only when the sending Safe logged it
  • When: the whole last year first; if an answer is over one page, 12 one-day windows a month apart; at most 240 studied by default
  • Match: the sender's own calls and arguments against the template's rules; card values are not judged. Exactly the template, its shape outside the registry, or a misfit; proven Safe or EOA
  • Trace: each one exactly the template, through drpc: who calls whom inside, to test the AI's flow lines
  • Amounts against balances, for tolerances; the spread of each free number
  • Your Safe is left out and its address removed from recordings

AI agentsteps 5, 6, 7

7Write the template and the notes

  • Protocol health: hacks, audits, upgrades, admin changes, each with its source
  • template.json: a rule for every argument, the effects, any views, computed fields with their slippage, each choice with a reason
  • docs.json: one official page per function
  • notes.json: title, verdict, each contract's role, each argument's meaning, up to 4 flow lines (after which call, from, to, function, text, sources), a review of every result the signer must look at
  • Test transactions, from other Safes
Why data, not code: the AI picks from the program's vocabulary; it never writes code that becomes a check.

Program · perturb, reportsteps 6, 7

8Record and write the report

  • perturb: changes each free field of each test transaction and simulates every copy; each must revert, be refused, or change nothing
  • report --record keeps only the live answers the checks read, or writes nothing if a read got none
  • Writes report.generated.md, and the HTML report in each language notes.json holds (for an instance, both files), from the recordings and the notes; compares each flow line with the traces
  • Refuses notes with a result left unreviewed, a review of a result that needs none, an unknown name, or a flow line outside the template
  • pnpm test computes every report again from the recordings, offline
Why record: CI has no keys, so it replays the answers. A recording shows what the report was computed from, not that it is true; box 10 checks that.

AI agentstep 7

9Open a pull request

  • The template, its test transactions and perturb recordings
  • Registry entries and markets, with their code pins
  • docs.json, notes.json, the report and its recordings
  • One report per operation, or per operation and instance when the card picks one, a vault today (instances/<instance>/); no report, no signing

Signerstep 8

10Review and merge

  • Read the report (below) and the template's rules
  • From main: pnpm report … --compare --data origin/<branch>, with --instance-of <instance> per instance report
  • It reads the facts again live, past transactions and their traces included (the search and signed messages stay recorded), and needs the HTML byte for byte
  • It refuses a branch that also changes the verdict core, and prints PROGRAM CHANGE and AI TEXT
  • Merging is your approval; branch protection on main is recommended
Why --compare: the recordings come from the AI's computer; main's code reads every fact again live and compares it with the report, so a pull request cannot weaken its own check.

Who merges what

  • Template or registry: the signer, after the report and --compare
  • Program: the AI, once pnpm program-gate, run from main's code, prints ELIGIBLE (canaries pass, no test dropped) and a fresh reviewer finds no regression
  • Program gate (the canaries, their list, the code that enforces these rules): the signer, never the AI
A branch changing the verdict core beside templates/, registry/ or the gate is refused by check-push, CI, --compare and program-gate until it is split.

Program · verifyself-check

16Check itself first

  • Installed packages equal their pins, before any loads
  • Every origin URL is your fork; fetch its main
  • Every object hashes to its name
  • The clone is exactly that commit, or nothing is verified
  • Then, before any chain read: refuses a card naming an instance with no report, or an entry without an attribute the template reads
Why: the checks that run are the ones on your main.
Program · verifystep 12

17Check the transaction

  1. The template's hash is the one you approved
  2. Floors: no delegatecall but to the official MultiSend; no unlimited approval but a registry standing allowance; no Safe setting change but a declared owner or threshold change; no MultiSend item sent to address zero; zero fee fields
  3. Fields: decode, re-encode byte for byte, every field against the template and the card; a signed message fetched by its digest must hash to it
  4. Each vault's asset() is its registry token
  5. Code: every registry contract the transaction or card names, or a card reference's attribute names, inside packed calls and signed messages too, with each message's verifyingContract, runs its pinned code
  6. Mutations: each bound field changed must give MISMATCH, or the verdict is UNVERIFIABLE
AlchemydrpcOrder API, e.g. CoW
Why mutations: they prove the template would catch a change to this very transaction.

Hardware wallet

Local only, never pushed: $KISS_SIGN_HOME

  • Config: the Safe, the repository to trust, the language
  • API keys in .env
  • Address book
  • Sealed cards and verdict files
  • Approved template hashes
Two providersEvery state, code, receipt and simulation read goes to Alchemy and drpc; if they disagree, the result is UNVERIFIABLE. Three research reads have one source and reach no verdict: the past-transaction search (Alchemy Transfers and Etherscan, an event Etherscan alone), call traces (drpc alone, checked against the transaction and receipt both providers give), and holder candidates (Alchemy Transfers). A signed message comes from one API and must hash to the digest the transaction holds.
Pinned downloadssolc, the Public Suffix List and the ERC-7730 archive load on first use, refused unless the sha256 is pinned. Signing reads none of them, and checks every installed package it loads against its pin.
Doubt fails closedAn AI fooled during signing can at worst cause MISMATCH or UNVERIFIABLE, while the program is your main. The basic tier stops attacks from outside kiss-sign, such as a tampered Safe web app, provided you compare every character of both hashes on the wallet and nothing on your computer writes the clone or $KISS_SIGN_HOME. A program rewritten on your computer, a template wrong when you merged it, or an AI-merged program change no canary catches is not caught; in the hardened tier the independent check still shows what is signed.
