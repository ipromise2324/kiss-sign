  • 原始碼驗證 5 / 5 Etherscan 上驗證的原始碼用固定版本的編譯器重新編譯，跟鏈上的程式碼一模一樣，所以解碼交易用的函式定義確實屬於這些合約。rlusd 重新編譯後只有 metadata hash 跟鏈上不同，所以函式選擇器和參數型別有證明，算通過；參數名稱沒有證明。morpho-blue、adaptive-curve-irm、sentora-rlusd-main-v2-e6bf-market-adapter、morpho-oracle-kbtc-rlusd-86 沒有呼叫直接打到，也不用它的函式定義解碼，所以沒有證明，不算在內；它跑的程式碼在「合約沒被換掉」比對。
  • 合約沒被換掉 9 / 9 每次簽名都確認卡片用到的每個合約還是研究時那份程式碼。被升級或換掉就擋下。vault-v2-factory、morpho-market-v1-adapter-v2-factory 簽名時不碰，只有報告比對它的程式碼。morpho-blue、adaptive-curve-irm、sentora-rlusd-main-v2-e6bf-market-adapter、morpho-oracle-kbtc-rlusd-86 沒有 ABI 證明比對它今天的程式碼，報告另外在最新區塊讀它跑的程式碼，跟 code pin 現在那一份比對。
  • 參數保護 沒有測試 模板沒有不限的參數：每個參數都綁定卡片或固定值，沒有參數要換值測試，所以沒有換值測試的記錄。每次簽名，verify 都把每個綁定的參數逐一改掉，確認都變成 MISMATCH。
  • 雙節點比對 鏈上資料都同時問兩家節點，答案不一樣就不給結果。研究時有三種資料只有一個來源，都不會影響判定：過去交易的呼叫追蹤（drpc）、搜尋過去交易（Alchemy 或 Etherscan 找到的都算，找事件只用 Etherscan），和金庫曾經收過份額的地址名單（Alchemy，每個地址的餘額仍問兩家）。

用 Ledger 簽的話，先在 Ethereum app 的設定打開「Transaction hash」：套用描述檔時，要打開它裝置才會顯示 domain hash 和 message hash。比對這兩個 hash 才是 kiss-sign 靠的檢查，解讀看起來再對也要比。

下一步

  1. 核准前，到「地址」逐一打開每個地址的來源，確認每個網域都是協議自己的，而且頁面上列著這個地址。
  2. 第一次用這個模板，或模板改過之後，先核准它
    pnpm kiss-sign template approve morpho/vault-v2-cap-accept

    它印出模板、GitHub 上 main 的 commit 和模板的 keccak256。是你審過的那份才回答 y。

  3. 做卡片
    pnpm kiss-sign card new morpho/vault-v2-cap-accept

    你這份 clone 的 templates/ 或 registry/ 跟 GitHub 上的 main 不一樣時，它什麼都不問就停下，叫你先跑 git pull 。

  4. 金庫（vault）：它列出可選的合約，每個附完整地址。選 sentora-rlusd-main-v2-e6bf，地址是 0x6dC58a0FdfC8D694e571DC59B9A52EEEa780E6bf

    列表的編號可能跟別人的不同，照名字選；也可以直接打名字 sentora-rlusd-main-v2-e6bf 。

  5. 市場（market）：它列出每個市場的 id、lltv 和每個組成的完整地址。選你要的市場，id 要對。
  6. 金額（absolute-cap）：打 rlusd 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

    也可以打 max，等於 340282366920938463463374607431768211455 base units；card new 會印出模板寫的理由。

    AI為什麼可以打 max：2^128-1 是 Vault V2 能存的最大絕對上限；更大的值會 revert，所以卡片不收。

  7. 它印出整張卡片，每個名字都附完整地址，最後問 Is this what you mean to do? [y/N] 。全部是你要的才打 y 。

    它印出 Sealed card 0x… ，這是卡片的 hash，下一步要用。

  8. 在 Safe web app 提出交易（第一次用這個模板或這個合約，先用小額），複製它的 safeTxHash，然後跑
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH：它印出 safeTxHash 和一個網頁的路徑，網頁上有 domain hash、message hash 和比對清單，往下走。

    MISMATCH 或 UNVERIFIABLE：不要簽。看它列出的檢查，再看本報告「待確認」裡 AI 的判斷，可能說明原因。

  9. 加強等級：在獨立電腦上跑
    ./check.sh <nonce>

    它算出的 hash 跟硬體錢包比對；它的網頁上的比對清單跟 verify 網頁上的逐列比對。

  10. 硬體錢包上的 domain hash 和 message hash，跟 verify 網頁上的逐字比對，一樣才簽。

    用 Ledger 簽的話，先在 Ethereum app 的設定打開「Transaction hash」：套用描述檔時，要打開它裝置才會顯示 domain hash 和 message hash。比對這兩個 hash 才是 kiss-sign 靠的檢查，解讀看起來再對也要比。

    比對domain hash 和 message hash，都是 0x 開頭 64 個字元

程式每次簽名自動做的事

  • 每個參數符合上面的規則，重新編碼要一模一樣
  • 模擬後 Safe 的餘額一點都不能變
  • 沒有任何授權在交易後變高

  • sentora-rlusd-main-v2-e6bf.absoluteCap：absoluteCap 等於你填的金額
