Deposit into a Morpho vaultAI research

morpho/vault-deposit · hyperithm-usdc-apex-v2-9e2f

The Safe first approves VaultBundlesV1 for exactly the amount you type, then calls vaultBundlesV1Deposit on it: VaultBundlesV1 pulls the tokens from the Safe and deposits them into the vault you pick, and the vault mints the shares straight to the Safe. You do not type the minimum shares: the program computes them from the vault's own preview when you build the card, less a small slippage; a higher price per share makes the transaction fail. The old route through Bundler3 is refused: verify returns MISMATCH.AI research

  • Address sources 3 / 4 1 address has results for you to review; see "To review". The other 3 are all confirmed in at least 2 places.
  • Source verified 3 / 3 The source verified on Etherscan, compiled again with a pinned compiler, gives exactly the code on chain, so the function definitions used to decode the transaction belong to these contracts.
  • Code unchanged 4 / 4 At each signing, the program checks that every contract the card uses still runs the code it was researched with. An upgrade or a replacement is stopped. Signing does not touch vault-v2-factory; only the report compares its code.
  • Parameter checks 2 / 2 The program changed every bound argument of 2 test transactions one by one, and each must become a MISMATCH; an argument that takes any value must give the same result with another value.
  • Two providers Every chain read asks two providers; when they disagree, there is no result. Three research reads have one source, and none of them reaches a verdict: past transactions' call traces (drpc), the search for past transactions (a transaction either Alchemy or Etherscan finds counts; only Etherscan searches for an event), and the addresses that ever received a vault's shares (Alchemy; each one's balance is still read through both).

Where deposits goAI research

Your USDC stays idle in the vault after you deposit: no liquidity adapter is set (liquidityAdapter() is the zero address at block 26,490,392), so nothing moves it on in the same transaction. An allocator lends it out later with allocate. source 1 source 2 source 3

Which markets it lends toAI research

Allocators lend it to Morpho Blue USDC markets through the vault's one adapter, within caps the curator sets. Morpho's API on 2026-11-25 shows most of it with PT-reUSD-10DEC2026, mHyperBTC and PT-USDat-14JAN2027 as collateral; this changes whenever an allocator reallocates. source 1 source 2 source 3 source 4

Who can change itAI research

Two allocators can move funds between markets at any time, within the caps. The curator must wait 3 days to add an adapter or raise a cap, but can add an allocator, change the fees or set the withdrawal penalty at once. source 1 source 2 source 3 source 4

Getting the USDC backAI research

About 300,001 of the vault's 7.21 million USDC sits idle (block 26,490,392). A larger withdrawal fails until an allocator moves USDC back, or someone calls forceDeallocate, which charges a penalty (0 now; the curator can raise it to 2% at once). A market can return only what its borrowers have not borrowed. source 1 source 2 source 3

Next steps

  1. Before you approve, open each address's sources in Addresses and check that each domain is the protocol's own and that the page lists the address.
  2. The first time you use this template, or after it changes, approve it
    pnpm kiss-sign template approve morpho/vault-deposit

    It prints the template, the commit of main on GitHub and the template's keccak256. Answer y only if it is the one you reviewed.

  3. Make the card
    pnpm kiss-sign card new morpho/vault-deposit

    When templates/ or registry/ in your clone differs from main on GitHub, it stops before asking anything and tells you to run git pull first.

  4. vault: it lists the contracts you can pick, each with its full address. Pick hyperithm-usdc-apex-v2-9e2f, address 0x093272C07700d3cA5301C3Bf9B3A392624179E2F

    The numbers in the list may differ from someone else's, so pick by name; you can also type the name hyperithm-usdc-apex-v2-9e2f.

  5. amount: type the amount of usdc in whole tokens, such as 1250.5; thousands commas are allowed, such as 1,000,611.448606.

    The card it shows before asking [y/N] gives it both in whole tokens and in base units; check that the number is what you want.

  6. minimum to receive (min-shares): you do not type it. The protocol's app fills this value without asking its user, so the program computes it.

    It reads previewDeposit on chain, uses the answer only when both providers agree, prints the expected amount of hyperithm-usdc-apex-v2-9e2f, then takes 0.10% less (the protocol's default 0.03% plus a 0.07% margin), rounded down.

    Source of the default: github.com/morpho-org/sdks. Check that the expected amount and the final number it prints are reasonable.

  7. It prints the whole card, each name with its full address, and asks Is this what you mean to do? [y/N]. Type y only if all of it is what you want.

    It prints Sealed card 0x…, the card's hash, which the next step uses.

  8. Propose the transaction in the Safe web app (the first time you use this template or this contract, start with a small amount), copy its safeTxHash, then run
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH: it prints the safeTxHash and the path of a page with the domain hash, the message hash and the checklist. Go on.

    MISMATCH or UNVERIFIABLE: do not sign. Read the checks it lists, then the AI judgment under "To review" in this report, which may explain why.

  9. Hardened tier: on an independent computer, run
    ./check.sh <nonce>

    Compare the hashes it computes with the hardware wallet, and its page's checklist row by row with the verify page.

  10. Compare the domain hash and the message hash on the hardware wallet character by character with the verify page. Sign only if they are the same.
