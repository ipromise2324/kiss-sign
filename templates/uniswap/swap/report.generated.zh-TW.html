在 Uniswap v4 的 StablePair 池子兌換 USDC 和 USDTAI 研究

uniswap/swap

一次 Universal Router 的 execute，在 USDC/USDT 的 StablePair 池子賣出卡片上剛好的數量，換回至少卡片最低數量的另一種穩定幣，付給 Safe。事先需要給 router 的 Permit2 授權（uniswap/allow-router）；其他池子、其他路線、其他收款人或超過 30 分鐘的截止時間都會被拒絕。AI 研究

  • 地址來源 5 / 6 1 個地址有結果要你看，見「待確認」。其餘 5 個都至少在 2 個地方確認。
  • 原始碼驗證 1 / 1 Etherscan 上驗證的原始碼用固定版本的編譯器重新編譯，跟鏈上的程式碼一模一樣，所以解碼交易用的函式定義確實屬於這些合約。permit2、uniswap-v4-pool-manager、uniswap-stable-pair-hook 沒有呼叫直接打到，也不用它的函式定義解碼，所以沒有證明，不算在內；它跑的程式碼在「合約沒被換掉」比對。
  • 合約沒被換掉 6 / 6 每次簽名都確認卡片用到的每個合約還是研究時那份程式碼。被升級或換掉就擋下。permit2、uniswap-v4-pool-manager、uniswap-stable-pair-hook 沒有 ABI 證明比對它今天的程式碼，報告另外在最新區塊讀它跑的程式碼，跟 code pin 現在那一份比對。
  • 參數保護 1 / 1 程式把 1 筆測試交易的每個綁定參數逐一改掉，都要變成 MISMATCH；不限的參數換成別的值，結果要跟原本一樣。
  • 呼叫追蹤 4 / 4 程式在過去交易的呼叫追蹤裡找 AI 寫的每條流程線，也確認每筆動到錢的內部呼叫都有模板或流程線說明；4 項裡 4 項通過。追蹤只來自 drpc，其中代幣的轉帳和授權都跟兩家節點都同意的收據核對過。
  • 雙節點比對 鏈上資料都同時問兩家節點，答案不一樣就不給結果。研究時有三種資料只有一個來源，都不會影響判定：過去交易的呼叫追蹤（drpc）、搜尋過去交易（Alchemy 或 Etherscan 找到的都算，找事件只用 Etherscan），和金庫曾經收過份額的地址名單（Alchemy，每個地址的餘額仍問兩家）。
建議單純的穩定幣兌換；池子的手續費 hook 可由 Uniswap 治理升級，app 走其他路線時會得到 MISMATCH。AI 研究：要小心

下一步

  1. 核准前，到「地址」逐一打開每個地址的來源，確認每個網域都是協議自己的，而且頁面上列著這個地址。
  2. 第一次用這個模板，或模板改過之後，先核准它
    pnpm kiss-sign template approve uniswap/swap

    它印出模板、GitHub 上 main 的 commit 和模板的 keccak256。是你審過的那份才回答 y。

  3. 做卡片
    pnpm kiss-sign card new uniswap/swap

    你這份 clone 的 templates/ 或 registry/ 跟 GitHub 上的 main 不一樣時，它什麼都不問就停下，叫你先跑 git pull 。

  4. 代幣（sell-token）：它列出可選的代幣，每個附完整地址。選你要的那個，名字和完整地址都要對。
  5. 代幣（buy-token）：它列出可選的代幣，每個附完整地址。選你要的那個，名字和完整地址都要對。
  6. 金額（sell-amount）：打 你選的代幣（sell-token） 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

  7. 最少收到的數量（min-buy）：程式用你選的兩個代幣的獨立價格，替 sell-amount 算最少要收到多少。

    兩個代幣都有價格來源、又錨定同一個價格時，它問 app 顯示的滑價（按 Enter 是 0.50%，最多 1.00%），印出讀到的價格，取比較嚴的那個，扣掉滑價和 0.25% 餘裕，無條件捨去。核對 app 的最少收到數量不低於它印出的 你選的代幣（buy-token） 數量。

    其他情況程式不算，你填 app 顯示的最少收到數量：有價格時程式拿它跟價格比，比價格低超過 2.50% 或價格有疑問就要再填一次一樣的數量；有代幣沒有價格來源時，程式說沒有東西可以比。

  8. 它印出整張卡片，每個名字都附完整地址，最後問 Is this what you mean to do? [y/N] 。全部是你要的才打 y 。

    它印出 Sealed card 0x… ，這是卡片的 hash，下一步要用。

  9. 在 Safe web app 提出交易（第一次用這個模板，先用小額），複製它的 safeTxHash，然後跑
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH：它印出 safeTxHash 和一個網頁的路徑，網頁上有 domain hash、message hash 和比對清單，往下走。

    MISMATCH 或 UNVERIFIABLE：不要簽。看它列出的檢查，再看本報告「待確認」裡 AI 的判斷，可能說明原因。

  10. 加強等級：在獨立電腦上跑
    ./check.sh <nonce>

    它算出的 hash 跟硬體錢包比對；它的網頁上的比對清單跟 verify 網頁上的逐列比對。

  11. 硬體錢包上的 domain hash 和 message hash，跟 verify 網頁上的逐字比對，一樣才簽。

    用 Ledger 簽的話，先在 Ethereum app 的設定打開「Transaction hash」：套用描述檔時，要打開它裝置才會顯示 domain hash 和 message hash。比對這兩個 hash 才是 kiss-sign 靠的檢查，解讀看起來再對也要比。

    比對domain hash 和 message hash，都是 0x 開頭 64 個字元

程式每次簽名自動做的事

  • 交易只有這 1 個呼叫，MultiSend 也一個個解開
  • 每個參數符合上面的規則，重新編碼要一模一樣
  • 模擬後 Safe 給出的 你選的代幣（sell-token） 剛好是你填的金額
  • 模擬後 Safe 收到 你選的代幣（buy-token），不少於程式算的最少收到的數量
  • 沒有任何授權在交易後變高
  • 卡片用到的每個登記合約，程式碼還是 code pin 記錄的那份
