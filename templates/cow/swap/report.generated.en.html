Place a sell order on CoW Swap (token allowance already in place)AI research

cow/swap

The Safe calls setPreSignature on CoW's settlement contract to pre-sign a sell order. A solver can then fill it until it expires (the app sets 30 minutes). The transaction holds only the order's hash. verify reads the full order back from CoW's API, computes the same hash, then compares the tokens, amounts and recipient one by one. The token to sell must first have an allowance for CoW's vault relayer.AI research

  • Transaction addresses 7 / 7 All 7 addresses are confirmed in at least 2 places: the official page (a github.com file counts as its GitHub organization, a place apart from the docs site), the protocol API, CoinGecko, the registered factory (with each other contract its check asks), the Immunefi bug bounty scope, the pinned SDK package or a shared deployer lists the same address.
  • Source verified 7 / 7 The source verified on Etherscan, compiled again with a pinned compiler, gives exactly the code on chain, so the function definitions used to decode the transaction belong to these contracts. usdc, usdt: compiled again, only the metadata hash differs from the code on chain, so their function selectors and parameter types are proven and they count as passed; their parameter names are not proven.
  • Code unchanged 7 / 7 At each signing, the program checks that every contract the card uses still runs the code it was researched with. An upgrade or a replacement is stopped.
  • Parameter checks no tests The only values that may be anything are in the signed order, locked by its hash, and they are not perturbed. The template has no argument that takes any value: each is bound to the card or to a fixed value, so nothing needs a perturbation test and none is recorded. At each signing, verify changes every bound argument one by one and checks that each becomes a MISMATCH.
  • Two providers Every chain read asks two providers; when they disagree, there is no result. Three research reads have one source, and none of them reaches a verdict: past transactions' call traces (drpc), the search for past transactions (a transaction either Alchemy or Etherscan finds counts; only Etherscan searches for an event), and the addresses that ever received a vault's shares (Alchemy; each one's balance is still read through both).
AdviceThe hash locks the order's contents. Note that verify depends on the CoW API to read the order back.AI research: be careful

Next steps

  1. Before you approve, open each address's sources in Addresses and check that each domain is the protocol's own and that the page lists the address.
  2. The first time you use this template, or after it changes, approve it
    pnpm kiss-sign template approve cow/swap

    It prints the template, the commit of main on GitHub and the template's keccak256. Answer y only if it is the one you reviewed.

  3. Make the card
    pnpm kiss-sign card new cow/swap

    When templates/ or registry/ in your clone differs from main on GitHub, it stops before asking anything and tells you to run git pull first.

  4. token (sell-token): it lists each token you can pick, with its full address. Pick the one you want; both its name and its full address must be right.
  5. token (buy-token): it lists each token you can pick, with its full address. Pick the one you want; both its name and its full address must be right.
  6. amount (sell-amount): type the amount of the token (sell-token) you pick in whole tokens, such as 1250.5; thousands commas are allowed, such as 1,000,611.448606.

    The card it shows before asking [y/N] gives it both in whole tokens and in base units; check that the number is what you want.

  7. amount (min-buy): type the amount of the token (buy-token) you pick in whole tokens, such as 1250.5; thousands commas are allowed, such as 1,000,611.448606.

    The card it shows before asking [y/N] gives it both in whole tokens and in base units; check that the number is what you want.

  8. It prints the whole card, each name with its full address, and asks Is this what you mean to do? [y/N]. Type y only if all of it is what you want.

    It prints Sealed card 0x…, the card's hash, which the next step uses.

  9. Propose the transaction in the Safe web app (the first time you use this template, start with a small amount), copy its safeTxHash, then run
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH: it prints the safeTxHash and the path of a page with the domain hash, the message hash and the checklist. Go on.

    MISMATCH or UNVERIFIABLE: do not sign. Read the checks it lists, then the AI judgment under "To review" in this report, which may explain why.

  10. Hardened tier: on an independent computer, run
    ./check.sh <nonce>

    Compare the hashes it computes with the hardware wallet, and its page's checklist row by row with the verify page.

  11. Compare the domain hash and the message hash on the hardware wallet character by character with the verify page. Sign only if they are the same.

    On a Ledger, first turn on "Transaction hash" in the Ethereum app's settings: with a descriptor applied, the device shows the domain hash and the message hash only when it is on. Comparing those hashes is the check kiss-sign relies on, however right the decoded fields look.

    Comparethe domain hash and the message hash, each 0x followed by 64 characters

What the program does at each signing

  • No allowance is higher after the transaction
  • Every registry contract the card uses still runs the code its code pin records
