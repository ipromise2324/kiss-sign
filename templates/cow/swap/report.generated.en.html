cow/swap

The Safe calls setPreSignature on CoW's settlement contract to pre-sign one sell order: exactly the card amount, for at least the card minimum, paid to the Safe. Needs an allowance to CoW's vault relayer first. Refuses buy, partial and fee orders.AI research

  • Transaction addresses 4 / 4 All 4 addresses are confirmed in at least 2 places: the official page (a github.com file counts as its GitHub organization, a place apart from the docs site), the protocol API, CoinGecko, the registered factory (with each other contract its check asks), the Immunefi bug bounty scope, the pinned SDK package or a shared deployer lists the same address.
  • Reference addresses 4 / 4 These 4 reference addresses need 1 place: the transaction never touches them, and card new only reads a number from them, which you confirm. A wrong price source lowers the minimum, and a pool's mean price checks it only when the pair has a pool.
  • Source verified 7 / 7 The source verified on Etherscan, compiled again with a pinned compiler, gives exactly the code on chain, so the function definitions used to decode the transaction belong to these contracts. usdc, usdt, chainlink-usdc-usd, chainlink-usdt-usd: compiled again, only the metadata hash differs from the code on chain, so their function selectors and parameter types are proven and they count as passed; their parameter names are not proven. gpv2-vault-relayer: no call goes to it directly and no function definition of it decodes anything, so it has no proof and is not counted; the code it runs is compared under "Code unchanged".
  • Code unchanged 8 / 8 At each signing, the program checks that every contract the card uses still runs the code it was researched with. An upgrade or a replacement is stopped. Signing does not touch chainlink-usdc-usd, chainlink-usdt-usd, uniswap-v3-factory, uniswap-v3-usdc-usdt-100; only the report compares their code. No ABI proof compares the code gpv2-vault-relayer runs today, so the report reads it at the latest block and compares it with the current code pin.
  • Parameter checks no tests The only values that may be anything are in the signed order, locked by its hash, and they are not perturbed. The template has no argument that takes any value: each is bound to the card or to a fixed value, so nothing needs a perturbation test and none is recorded. At each signing, verify changes every bound argument one by one and checks that each becomes a MISMATCH.
  • Two providers Every chain read asks two providers; when they disagree, there is no result. Three research reads have one source, and none of them reaches a verdict: past transactions' call traces (drpc), the search for past transactions (a transaction either Alchemy or Etherscan finds counts; only Etherscan searches for an event), and the addresses that ever received a vault's shares (Alchemy; each one's balance is still read through both).

Next steps

  1. Before you approve, open each address's sources in Addresses and check that each domain is the protocol's own and that the page lists the address.
  2. The first time you use this template, or after it changes, approve it
    pnpm kiss-sign template approve cow/swap

    It prints the template, the commit of main on GitHub and the template's keccak256. Answer y only if it is the one you reviewed.

  3. Make the card
    pnpm kiss-sign card new cow/swap

    When templates/ or registry/ in your clone differs from main on GitHub, it stops before asking anything and tells you to run git pull first.

  4. token (sell-token): it lists each token you can pick, with its full address. Pick the one you want; both its name and its full address must be right.
  5. token (buy-token): it lists each token you can pick, with its full address. Pick the one you want; both its name and its full address must be right.
  6. amount (sell-amount): type the amount of the token (sell-token) you pick in whole tokens, such as 1250.5; thousands commas are allowed, such as 1,000,611.448606.

    The card it shows before asking [y/N] gives it both in whole tokens and in base units; check that the number is what you want.

  7. minimum to receive (min-buy): the program computes the least to receive for sell-amount from an independent price of the two tokens you picked.

    usdc for usdt: computed when the live checks pass, from the price feeds chainlink-usdc-usd, chainlink-usdt-usd; the pool uniswap-v3-usdc-usdt-100 (liquidity at least 6660000000000) is a second source.

    usdt for usdc: computed when the live checks pass, from the price feeds chainlink-usdt-usd, chainlink-usdc-usd; the pool uniswap-v3-usdc-usdt-100 (liquidity at least 6660000000000) is a second source.

    When both tokens have a price feed and share a peg, it asks the slippage the app shows (Enter is 0.50%, at most 1.00%), prints the prices it read, and takes the stricter one less the slippage and a 0.25% margin, rounded down. The margin is the program's, the same for every pair: room for the feeds' own error and a fee inside the app's minimum. Check that the app's minimum received is not below the amount of the token (buy-token) you pick it prints.

    "Computed" holds only when card new's live checks pass at signing: each feed recent enough, each pegged token near its peg, the feeds and pools agreeing, and each pool deep enough and answering. When any fails, it says which, and you type the minimum received the app shows instead, twice.

    AIThe AI chose the minimum liquidity 6660000000000 of the pool uniswap-v3-usdc-usdt-100, not the protocol or its app. Why: pnpm pool-depth --auto over 366 daily samples: calm 41137149129847228 (block 25969908), stressed and lowest 6660026988514 (block 26301108), 30-minute window, the one this pegged pair is priced at. I took the lowest, rounded down to 6660000000000, so the pool still prices on a day as thin as the worst measured; 0 of 366 days fall under it.

  8. It prints the whole card, each name with its full address, and asks Is this what you mean to do? [y/N]. Type y only if all of it is what you want.

    It prints Sealed card 0x…, the card's hash, which the next step uses.

  9. Propose the transaction in the Safe web app (the first time you use this template, start with a small amount), copy its safeTxHash, then run
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH: it prints the safeTxHash and the path of a page with the domain hash, the message hash and the checklist. Go on.

    MISMATCH or UNVERIFIABLE: do not sign. Read the checks it lists, then the AI judgment under "To review" in this report, which may explain why.

  10. Hardened tier: on an independent computer, run
    ./check.sh <nonce>

    Compare the hashes it computes with the hardware wallet, and its page's checklist row by row with the verify page.

  11. Compare the domain hash and the message hash on the hardware wallet character by character with the verify page. Sign only if they are the same.

    On a Ledger, first turn on "Transaction hash" in the Ethereum app's settings: with a descriptor applied, the device shows the domain hash and the message hash only when it is on. Comparing those hashes is the check kiss-sign relies on, however right the decoded fields look.
