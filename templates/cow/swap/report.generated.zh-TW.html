在 CoW Swap 下賣單（代幣已授權）AI 研究

cow/swap

Safe 呼叫 CoW 結算合約的 setPreSignature，預先簽下一張賣單；solver 之後在 30 分鐘內成交。交易裡只有訂單的雜湊，verify 從 CoW 的 API 讀回訂單原文，算出同一個雜湊後，再逐項比對代幣、數量、收款人。賣的代幣要先授權給 CoW 的 vault relayer。AI 研究

  • 地址來源 7 / 7 7 個地址都至少在 2 個地方確認：官方頁（GitHub 上的檔案算它的 GitHub 組織，跟文件網站是不同的地方）、協議 API、CoinGecko、登記工廠（連同它的檢查問到的其他合約）、Immunefi 漏洞賞金範圍、釘選的 SDK 套件或共用的部署者列出同一個地址。
  • 原始碼驗證 5 / 5 Etherscan 上驗證的原始碼用固定版本的編譯器重新編譯，跟鏈上的程式碼一模一樣，所以解碼交易用的函式定義確實屬於這些合約。
  • 合約沒被換掉 7 / 7 每次簽名都確認卡片用到的每個合約還是研究時那份程式碼。被升級或換掉就擋下。
  • 參數保護 沒有測試 交易裡不限的值只在簽的訂單裡，由雜湊鎖住，不換值測試。模板沒有不限的參數：每個參數都綁定卡片或固定值，沒有參數要換值測試，所以沒有換值測試的記錄。每次簽名，verify 都把每個綁定的參數逐一改掉，確認都變成 MISMATCH。
  • 雙節點比對 鏈上資料都同時問兩家節點，答案不一樣就不給結果。研究時有三種資料只有一個來源，都不會影響判定：過去交易的呼叫追蹤（drpc）、搜尋過去交易（Alchemy 或 Etherscan 找到的都算，找事件只用 Etherscan），和金庫曾經收過份額的地址名單（Alchemy，每個地址的餘額仍問兩家）。
建議訂單內容由雜湊鎖住；要注意 verify 依賴 CoW API 讀回訂單。AI 研究：要小心

過去交易

過去的記錄裡，跟模板一模一樣的有 24 筆：Safe 22 筆（19 個 Safe）、EOA 2 筆（1 個地址，各自送模板的一個呼叫）；形狀一樣、但用的是 registry 外的地址的有 119 筆：Safe 114 筆（85 個 Safe）、EOA 5 筆（5 個地址，各自送模板的一個呼叫）；形狀不同的有 167 筆，列在其他做法。這些交易全部成功執行：它們是從 gpv2-settlement PreSignature時的事件紀錄（log）找到的，失敗的交易不會留下這種紀錄。一模一樣的最近 3 筆：0xdab061be…、0x846277d0…、0xd7e08fb4…。形狀一樣的最近 3 筆：0x07540e9a…、0x2b01d376…、0xb788eac3…。

其他做法

只算用了這個操作的呼叫的交易。跟模板一模一樣，指交易的呼叫和參數位置跟模板相同，從交易本身看得出來的參數規定（例如該填送出者的地方、固定值）都成立，模板綁定 registry 合約的地方也是模板允許的合約。形狀一樣、但用的是 registry 外的市場、代幣、金庫或地址，指呼叫、參數位置和這些參數規定都一樣，但有地址或市場不在 registry 裡；種類照記錄看得出的寫，看不出就只說地址。其他的依原因分組，各附最多 3 筆例子。

下一步

  1. 核准前，打開「地址」裡每個地址列出的來源：確認每個網域是協議自己的，而且頁面上列著這個地址。
  2. 第一次用這個模板，或模板改過之後，先核准它
    pnpm kiss-sign template approve cow/swap

    它印出模板、GitHub 上 main 的 commit 和模板的 keccak256。是你審過的那份才回答 y。

  3. 做卡片
    pnpm kiss-sign card new cow/swap

    你這份 clone 的 templates/ 或 registry/ 跟 GitHub 上的 main 不一樣時，它什麼都不問就停下，叫你先跑 git pull 。

  4. 代幣（sell-token）：它列出可選的代幣，每個附完整地址。選你要的那個，名字和完整地址都要對。
  5. 代幣（buy-token）：它列出可選的代幣，每個附完整地址。選你要的那個，名字和完整地址都要對。
  6. 金額（sell-amount）：打 你選的代幣（sell-token） 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

  7. 金額（min-buy）：打 你選的代幣（buy-token） 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

  8. 它印出整張卡片，每個名字都附完整地址，最後問 Is this what you mean to do? [y/N] 。全部是你要的才打 y 。

    它印出 Sealed card 0x… ，這是卡片的 hash，下一步要用。

  9. 在 Safe web app 提出交易（第一次用這個模板，先用小額），複製它的 safeTxHash，然後跑
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH：它印出 safeTxHash 和一個網頁的路徑，網頁上有 domain hash、message hash 和比對清單，往下走。

    MISMATCH 或 UNVERIFIABLE：不要簽。看它列出的檢查，再看本報告「待確認」裡 AI 的判斷，可能說明原因。

  10. 加強等級：在獨立電腦上跑
    ./check.sh <nonce>

    它算出的 hash 跟硬體錢包比對；它的網頁上的比對清單跟 verify 網頁上的逐列比對。

  11. 硬體錢包上的 domain hash 和 message hash，跟 verify 網頁上的逐字比對，一樣才簽。

    用 Ledger 簽的話，先在 Ethereum app 的設定打開「Transaction hash」：套用描述檔時，要打開它裝置才會顯示 domain hash 和 message hash。比對這兩個 hash 才是 kiss-sign 靠的檢查，解讀看起來再對也要比。

    比對domain hash 和 message hash，都是 0x 開頭 64 個字元

程式每次簽名自動做的事

  • 交易只有這 1 個呼叫，MultiSend 也一個個解開
  • 每個參數符合上面的規則，重新編碼要一模一樣
  • 模擬後 Safe 的餘額一點都不能變
  • 沒有任何授權在交易後變高
  • 卡片用到的每個登記合約，程式碼還是 code pin 記錄的那份
