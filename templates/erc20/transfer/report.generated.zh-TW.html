從 Safe 轉出 ERC-20 代幣AI 研究

erc20/transfer

Safe 直接呼叫你選的代幣合約的 transfer，把你填的金額轉給你選的收款人。只有一個呼叫，不經過任何路由或其他合約，也不留下授權。AI 研究

  • 地址來源 5 / 6 1 個地址有結果要你看，見「待確認」。其餘 5 個都至少在 2 個地方確認。
  • 原始碼驗證 6 / 6 Sourcify 的原始碼用固定版本的編譯器重新編譯，跟鏈上的程式碼一模一樣，所以解碼交易用的函式定義確實屬於這些合約。
  • 合約沒被換掉 6 / 6 每次簽名都確認卡片用到的每個合約還是研究時那份程式碼。被升級或換掉就擋下。
  • 參數保護 沒有測試 模板沒有不限的參數：每個參數都綁定卡片或固定值，沒有參數要換值測試，所以沒有換值測試的記錄。每次簽名，verify 都把每個綁定的參數逐一改掉，確認都變成 MISMATCH。
  • 雙節點比對 所有鏈上資料都同時問兩家節點，答案不一樣就不給結果。

過去交易

過去的記錄裡，跟模板一模一樣的有 270 筆：Safe 0 筆、EOA 270 筆（243 個地址，各自送模板的一個呼叫）；形狀一樣、但用的是 registry 外的代幣的有 27 筆：Safe 1 筆（1 個 Safe）、EOA 26 筆（14 個地址，各自送模板的一個呼叫）；形狀不同的有 9 筆，列在其他做法。這些交易全部成功執行：它們是從 usdc 轉帳時、usdt 轉帳時、0x5aFE3855358E112B5647B952709E6165e1c1eEEe 轉帳時的 Transfer 紀錄找到的，失敗的交易不會留下紀錄。一模一樣的最近 3 筆：0x8189fd30…、0x82073d9a…、0xb5df0991…。形狀一樣的最近 3 筆：0xabf7c503…、0xcb5d4725…、0x7b6ca7b1…。

其他做法

只算用了這個操作的呼叫的交易。跟模板一模一樣，指交易的呼叫和參數位置跟模板相同，從交易本身看得出來的參數規定（例如該填送出者的地方、固定值）都成立，模板綁定 registry 合約的地方也是模板允許的合約。形狀一樣、但用的是 registry 外的市場、代幣、金庫或地址，指呼叫、參數位置和這些參數規定都一樣，但有地址或市場不在 registry 裡；種類照記錄看得出的寫，看不出就只說地址。其他的依原因分組，各附最多 3 筆例子。

下一步

  1. 第一次用這個模板，或模板改過之後，先核准它
    bin/kiss-sign template approve erc20/transfer

    它印出模板、GitHub 上 main 的 commit 和模板的 keccak256。是你審過的那份才回答 y。

  2. 收款人不是你的 Safe 時，先把它加進地址簿。名字自己取，用小寫英文和 - 連接；地址從聊天以外的來源取得
    bin/kiss-sign book add <name> <address>

    它印出名字和完整地址，問 Add this entry? [y/N] 。每個字元都跟聊天以外的來源核對過才打 y 。同一個收款人只要加一次。

  3. 做卡片
    bin/kiss-sign card new erc20/transfer

    你這份 clone 的 templates/ 或 registry/ 跟 GitHub 上的 main 不一樣時，它什麼都不問就停下，叫你先跑 git pull 。

  4. 代幣（token）：它列出可選的代幣，每個附完整地址。選你要的那個，名字和完整地址都要對。
  5. 收款人（recipient）：它列出你的 Safe 和地址簿裡的名字，每個附完整地址。選你要的那個，完整地址要對。
  6. 金額（amount）：打 你選的代幣 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

  7. 它印出整張卡片，每個名字都附完整地址，最後問 Is this what you mean to do? [y/N] 。全部是你要的才打 y 。

    它印出 Sealed card 0x… ，這是卡片的 hash，下一步要用。

  8. 在 Safe web app 提出交易（第一次用這個模板，先用小額），複製它的 safeTxHash，然後跑
    bin/kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH：它印出 safeTxHash 和一個網頁的路徑，網頁上有 domain hash、message hash 和比對清單，往下走。

    MISMATCH 或 UNVERIFIABLE：不要簽。看它列出的檢查，再看本報告「待確認」裡 AI 的判斷，可能說明原因。

  9. 加強等級：在獨立電腦上跑
    ./check.sh <nonce>

    它算出的 hash 跟硬體錢包比對；它的網頁上的比對清單跟 verify 網頁上的逐列比對。

  10. 硬體錢包上的 domain hash 和 message hash，跟 verify 網頁上的逐字比對，一樣才簽。
    比對domain hash 和 message hash，都是 0x 開頭 64 個字元

程式每次簽名自動做的事

  • 交易只有這 1 個呼叫，MultiSend 也一個個解開
  • 每個參數符合上面的規則，重新編碼要一模一樣
  • 模擬後 Safe 給出的 你選的代幣 剛好是你填的金額
  • 沒有任何授權在交易後變高
  • 卡片用到的每個登記合約，程式碼還是 code pin 記錄的那份
