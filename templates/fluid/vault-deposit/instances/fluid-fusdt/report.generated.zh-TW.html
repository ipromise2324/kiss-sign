把代幣存進 Fluid 出借代幣（fToken）AI 研究

fluid/vault-deposit · fluid-fusdt

Safe 先核准 fToken 動用剛好金額的資產（例如 USDC），再呼叫 fToken 的一般 deposit，換得 fToken 份額。需要一個有報告的 fToken；其他核准對象、收款人或金額都會被拒絕。AI 研究

  • 交易地址 4 / 4 4 個地址都至少在 2 個地方確認：官方頁（GitHub 上的檔案算它的 GitHub 組織，跟文件網站是不同的地方）、協議 API、CoinGecko、登記工廠（連同它的檢查問到的其他合約）、Immunefi 漏洞賞金範圍、釘選的 SDK 套件或共用的部署者列出同一個地址。
  • 原始碼驗證 3 / 3 Etherscan 上驗證的原始碼用固定版本的編譯器重新編譯，跟鏈上的程式碼一模一樣，所以解碼交易用的函式定義確實屬於這些合約。usdt 重新編譯後只有 metadata hash 跟鏈上不同，所以函式選擇器和參數型別有證明，算通過；參數名稱沒有證明。fluid-liquidity 沒有呼叫直接打到，也不用它的函式定義解碼，所以沒有證明，不算在內；它跑的程式碼在「合約沒被換掉」比對。
  • 合約沒被換掉 4 / 4 每次簽名都確認卡片用到的每個合約還是研究時那份程式碼。被升級或換掉就擋下。fluid-lending-factory 簽名時不碰，只有報告比對它的程式碼。fluid-liquidity 沒有 ABI 證明比對它今天的程式碼，報告另外在最新區塊讀它跑的程式碼，跟 code pin 現在那一份比對。fluid-liquidity 依函式選擇器把呼叫分給各自的實作：seeds 接到的每個實作和它的函式清單也一樣確認，沒有 seed 接到的實作不檢查。
  • 參數保護 沒有測試 模板沒有不限的參數：每個參數都綁定卡片或固定值，沒有參數要換值測試，所以沒有換值測試的記錄。每次簽名，verify 都把每個綁定的參數逐一改掉，確認都變成 MISMATCH。
  • 呼叫追蹤 1 / 1 程式在過去交易的呼叫追蹤裡找 AI 寫的每條流程線，也確認每筆動到錢的內部呼叫都有模板或流程線說明；1 項裡 1 項通過。追蹤只來自 drpc，其中代幣的轉帳和授權都跟兩家節點都同意的收據核對過。
  • 雙節點比對 鏈上資料都同時問兩家節點，答案不一樣就不給結果。研究時有三種資料只有一個來源，都不會影響判定：過去交易的呼叫追蹤（drpc）、搜尋過去交易（Alchemy 或 Etherscan 找到的都算，找事件只用 Etherscan），和金庫曾經收過份額的地址名單（Alchemy，每個地址的餘額仍問兩家）。
建議把 USDT 一般 ERC-4626 存進規模大、長期持有的 fToken；最少份額只在簽署前檢查，且 USDT 發行方可凍結或更改代幣。AI 研究：要小心

下一步

  1. 核准前，到「地址」逐一打開每個地址的來源，確認每個網域都是協議自己的，而且頁面上列著這個地址。
  2. 第一次用這個模板，或模板改過之後，先核准它
    pnpm kiss-sign template approve fluid/vault-deposit

    它印出模板、GitHub 上 main 的 commit 和模板的 keccak256。是你審過的那份才回答 y。

  3. 做卡片
    pnpm kiss-sign card new fluid/vault-deposit

    你這份 clone 的 templates/ 或 registry/ 跟 GitHub 上的 main 不一樣時，它什麼都不問就停下，叫你先跑 git pull 。

  4. 金庫（vault）：它列出可選的合約，每個附完整地址。選 fluid-fusdt，地址是 0x5C20B550819128074FD538Edf79791733ccEdd18

    列表的編號可能跟別人的不同，照名字選；也可以直接打名字 fluid-fusdt 。

  5. 金額（amount）：打 usdt 的數量，用整顆幣，例如 1250.5 ；可以有千位逗號，例如 1,000,611.448606 。

    它在問 [y/N] 之前顯示的卡片列出整顆和 base units 兩種寫法，核對數字是你要的。

  6. 最少收到的數量（min-shares）：不用填。交易裡沒有這個值，所以程式自己算，verify 拿模擬的結果跟它比。

    它在鏈上讀 previewDeposit，兩個節點答案一樣才用，印出預期的 fluid-fusdt 數量，再少 0.10%（協議預設的 0.00%，再加 0.10% 餘裕），無條件捨去。

    預設值的來源：github.com/Instadapp/fluid-contracts-public。核對印出的預期數量跟最後的數字合理。

    AI0.10% 的餘裕：由 AI 選定，不是協議或它的 app 定的。理由：Fluid 對一般存款不設滑價，且每股價格只會上升。0.10% 大約足夠年化 9% 的情況下，交易執行前價格上升四天的幅度。

  7. 它印出整張卡片，每個名字都附完整地址，最後問 Is this what you mean to do? [y/N] 。全部是你要的才打 y 。

    它印出 Sealed card 0x… ，這是卡片的 hash，下一步要用。

  8. 在 Safe web app 提出交易（第一次用這個模板或這個合約，先用小額），複製它的 safeTxHash，然後跑
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH：它印出 safeTxHash 和一個網頁的路徑，網頁上有 domain hash、message hash 和比對清單，往下走。

    MISMATCH 或 UNVERIFIABLE：不要簽。看它列出的檢查，再看本報告「待確認」裡 AI 的判斷，可能說明原因。

  9. 加強等級：在獨立電腦上跑
    ./check.sh <nonce>

    它算出的 hash 跟硬體錢包比對；它的網頁上的比對清單跟 verify 網頁上的逐列比對。

  10. 硬體錢包上的 domain hash 和 message hash，跟 verify 網頁上的逐字比對，一樣才簽。

    用 Ledger 簽的話，先在 Ethereum app 的設定打開「Transaction hash」：套用描述檔時，要打開它裝置才會顯示 domain hash 和 message hash。比對這兩個 hash 才是 kiss-sign 靠的檢查，解讀看起來再對也要比。

    比對domain hash 和 message hash，都是 0x 開頭 64 個字元

程式每次簽名自動做的事

  • 交易只有這 2 個呼叫，MultiSend 也一個個解開
  • 每個參數符合上面的規則，重新編碼要一模一樣
  • 模擬後 Safe 給出的 usdt 剛好是你填的金額
  • 模擬後 Safe 收到 fluid-fusdt，不少於程式算的最少收到的數量
  • 沒有任何授權在交易後變高
  • 卡片用到的每個登記合約，程式碼還是 code pin 記錄的那份
