The Safe calls its own swapOwner, replacing the old signer with the new signer. The threshold does not change. The program computes prevOwner by reading getOwners on chain, so you do not type it.AI research

  • Address sources 2 / 2 All 2 addresses are confirmed in at least 2 places: the official page (a github.com file counts as its GitHub organization, a place apart from the docs site), the protocol API, CoinGecko, the registered factory (with each other contract its check asks), the Immunefi bug bounty scope, the pinned SDK package or a shared deployer lists the same address.
  • Source verified 2 / 2 The source verified on Etherscan, compiled again with a pinned compiler, gives exactly the code on chain, so the function definitions used to decode the transaction belong to these contracts.
  • Code unchanged 2 / 2 At each signing, the program checks that every contract the card uses still runs the code it was researched with. An upgrade or a replacement is stopped. Signing does not touch safe-1.3.0, safe-1.4.1; only the report compares their code.
  • Parameter checks no tests The template has no argument that takes any value: each is bound to the card or to a fixed value, so nothing needs a perturbation test and none is recorded. At each signing, verify changes every bound argument one by one and checks that each becomes a MISMATCH.
  • Two providers Every chain read asks two providers; when they disagree, there is no result. Three research reads have one source, and none of them reaches a verdict: past transactions' call traces (drpc), the search for past transactions (a transaction either Alchemy or Etherscan finds counts; only Etherscan searches for an event), and the addresses that ever received a vault's shares (Alchemy; each one's balance is still read through both).

Next steps

  1. Before you approve, open each address's sources in Addresses and check that each domain is the protocol's own and that the page lists the address.
  2. The first time you use this template, or after it changes, approve it
    pnpm kiss-sign template approve safe/swap-owner

    It prints the template, the commit of main on GitHub and the template's keccak256. Answer y only if it is the one you reviewed.

  3. First add each signer you will add, remove or replace to your address book. Pick a name in lowercase English joined with -; get the address from a source outside the chat
    pnpm kiss-sign book add <name> <address>

    It prints the name and the full address and asks Add this entry? [y/N]. Type y only after checking every character against a source outside the chat. Add each person once.

  4. Make the card
    pnpm kiss-sign card new safe/swap-owner

    When templates/ or registry/ in your clone differs from main on GitHub, it stops before asking anything and tells you to run git pull first.

  5. signer (old-owner): it lists the names in your address book, each with its full address. Pick the signer you want; its full address must be right.
  6. signer (new-owner): it lists the names in your address book, each with its full address. Pick the signer you want; its full address must be right.
  7. It prints the whole card, each name with its full address, and asks Is this what you mean to do? [y/N]. Type y only if all of it is what you want.

    It prints Sealed card 0x…, the card's hash, which the next step uses.

  8. Propose the transaction in the Safe web app, copy its safeTxHash, then run
    pnpm kiss-sign verify --card <card hash> --safe-tx-hash <safeTxHash>

    MATCH: it prints the safeTxHash and the path of a page with the domain hash, the message hash and the checklist. Go on.

    MISMATCH or UNVERIFIABLE: do not sign. Read the checks it lists, then the AI judgment under "To review" in this report, which may explain why.

  9. Hardened tier: on an independent computer, run
    ./check.sh <nonce>

    Compare the hashes it computes with the hardware wallet, and its page's checklist row by row with the verify page.

  10. Compare the domain hash and the message hash on the hardware wallet character by character with the verify page. Sign only if they are the same.

    On a Ledger, first turn on "Transaction hash" in the Ethereum app's settings: with a descriptor applied, the device shows the domain hash and the message hash only when it is on. Comparing those hashes is the check kiss-sign relies on, however right the decoded fields look.

What the program does at each signing

  • The transaction has only this call, counting each call inside a MultiSend
  • Every argument follows the rules above, and encoding them again gives exactly the same bytes
  • After simulation, no balance of the Safe may change at all
  • The Safe's signers and threshold are read before and after simulation: only what the card names may change; the modules, guard, fallback handler and singleton may not
  • No allowance is higher after the transaction
  • Every registry contract the card uses still runs the code its code pin records
